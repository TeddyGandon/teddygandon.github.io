Documentation

Squadron docs

Everything you need to run the experiment in your own repository: setup, how to write issues the agents can work from, what each agent does and doesn't do, and how the workflow is put together.

Introduction

Squadron is a GitHub repository template that runs a three-role AI engineering workflow on GitHub Actions. A coder, a reviewer and a tester agent, all running on GitHub Copilot CLI, take a labeled issue to a merged pull request. Status is tracked with issue labels, so no GitHub Project is needed.

It's an experiment

Squadron was built to find out how far agents get on their own. The loop works, but quality depends almost entirely on how well the issues are written. Use it on repositories where you can afford to review and revert what it merges.

How it works

  1. You write an issue from a form and add status:todo when it's ready. The issue is queued: Squadron works on one issue at a time.
  2. The coder checks the requirements. If something blocking is missing, it asks on the issue and stops. Otherwise it implements the issue, updates the docs and opens a pull request.
  3. The reviewer reads the diff against the issue and posts a verdict. Approved: on to the tester. Changes needed: back to the coder.
  4. The tester writes tests from the issue alone. The workflow runs the test command. Passing or failing, the pull request goes back to the coder.
  5. The coder merges after a passing run. If the pull request conflicts with its base branch, it resolves the conflicts first and sends it back through review and testing.
  6. GitHub reports the merge, the issue becomes status:done and the next queued issue starts.

Handoffs between agents happen through labels on the pull request (agent:coder, agent:reviewer, agent:tester). Each agent removes its trigger label when it starts, so re-applying a label is always enough to run that step again.

Quick start

  1. Create your product repository from the template: Use this template.
  2. Add the COPILOT_GITHUB_TOKEN and SQUADRON_GITHUB_TOKEN secrets.
  3. Run Actions → Squadron Setup → Run workflow. It's safe to run again at any time.
  4. Open an issue from the Feature, Technical task or Bug form, then add status:todo.

Replace the template's README.md with your product's own. Template documentation lives in SQUADRON.md, USAGE.md and SQUADRON-CHANGELOG.md, which the update workflow keeps current.

Secrets

Create these in Settings → Secrets and variables → Actions.

SecretWhat it isWhere it's used
COPILOT_GITHUB_TOKEN A token authorized to use GitHub Copilot. Copilot CLI steps only. It's stripped from Copilot's own shell environment.
SQUADRON_GITHUB_TOKEN A fine-grained token for this repository with Contents, Pull requests, Issues and Workflows set to read and write. Approve it for the organization if required. Pull requests, labels, comments, pushes and merges, plus the update workflow. Never present in a Copilot step.

Setup workflow

Run Actions → Squadron Setup → Run workflow after adding the secrets. It's safe to run any number of times, and the update workflow runs it automatically after every update. It:

  • creates the status:*, agent:* and directive:* labels, or updates the color and description of existing ones;
  • creates one model label per line of .github/squadron-models.txt, and deletes model labels that are no longer listed (which also removes them from issues);
  • checks that both secrets are present;
  • checks that SQUADRON_GITHUB_TOKEN can write to the repository.

Run the setup before labeling your first issue.

Variables

Optional repository variables, for when the defaults don't fit your product:

VariableDefaultPurpose
SQUADRON_TEST_COMMANDnpm run testThe command the workflow runs as the merge gate.
SQUADRON_TEST_PATHS**/*.test.*,**/*.spec.*Comma-separated git glob patterns for test files, anywhere in the repository. Only matching files (plus npm manifests) are committed by the tester.

Branch protection

Configure branch protection and required checks as you like: they stay authoritative. The reviewer's verdict is a pull request comment, not a GitHub approval review.

When the coder's direct merge is blocked, for example by required checks still running on the tester's commit, it enables auto-merge instead. If you use required checks, turn on Settings → General → Allow auto-merge.

Issue forms

The issue title and body are the coder's requirements and the tester's only source of expected behavior. Agents don't read comments. Three forms structure that input:

Feature

[Feature]:

  • Problem or opportunity required
  • Proposed behavior required
  • Acceptance criteria required
  • Scope and constraints
  • Additional context

Technical task

[Technical]:

  • Objective required
  • Context and motivation required
  • Constraints or proposed approach
  • Acceptance criteria required
  • References

Bug report

[Bug]:

  • Bug summary required
  • Actual behavior required
  • Expected behavior required
  • Steps to reproduce required
  • Environment
  • Fix acceptance criteria required
  • Logs or screenshots

The forms don't apply any label: add status:todo yourself when the issue is ready, whether it comes from a form or not.

Tips for issues that hold up

  • Write observable acceptance criteria: inputs, outputs, messages, files, exit codes, UI states.
  • Say what must not change, especially behavior delivered by earlier issues.
  • Describe mockups and screenshots in text: an image the agent can't interpret is a missing requirement.
  • Make the choices: "A or B?" and "TBD" will stop the coder.
  • If the work needs a GitHub Actions workflow, say a person will add it, or scope it out: see what agents can't change.

Requirements check

Before writing any code, the coder runs the squadron-requirements-checker skill on the issue title and body, and researches the repository for anything the issue mentions. A gap is blocking only if:

  • two reasonable engineers could implement it in materially different ways, with no basis to choose;
  • the tester couldn't decide pass or fail from the issue alone;
  • it conflicts with the repository or with itself in a way that changes the result;
  • it depends on information the agents can't access, like a private link or an image with no text description;
  • it needs work the agents aren't allowed to deliver, like a file under .github/workflows, unless the issue marks that part out of scope or manual.

Conventional choices that follow the repository's existing patterns are not blocking. When the issue is not ready, the coder posts a comment starting with ## Squadron requirements check listing each question and removes the issue's status label without implementing anything. The issue leaves the queue, and the next queued issue starts.

To continue: answer the questions in the issue body (not in a comment), then add status:todo again.

The checker returns a JSON verdict, which the workflow turns into that comment:

{
  "ready": false,
  "summary": "One or two sentences on the overall state of the requirements.",
  "missing_requirements": [
    {
      "topic": "Error handling",
      "question": "What should the export do when the list is empty?",
      "reason": "The tester can't decide pass or fail without it."
    }
  ]
}

To skip the check for one issue, add directive:skip-requirements-check before it starts: see issue directives.

Requirements helper

The squadron-requirements-helper Copilot skill helps you draft an issue that passes the check. Give it a rough idea, notes, logs or specs: it researches the repository, asks a few focused questions, and returns a paste-ready title and body using the exact headings of the matching form. It never creates the issue or applies labels for you. If the request needs a GitHub Actions workflow, it helps you scope it to what the agents can deliver.

Issue directives

Add directive:* labels to an issue, before it starts, to change how the agents handle it. Every agent reads them from the issue, including on later review, test and fix runs.

LabelEffect
directive:skip-requirements-checkThe coder implements the issue directly, without the requirements check.
directive:use-model-<model>-cost-<tier>Every agent (coder, reviewer and tester) runs Copilot with that model instead of the default.

Available models

The models come from .github/squadron-models.txt, which lists models included in Copilot Pro. The cost tier is the model's relative price per 1M output tokens, from GitHub's pricing: low under $2, medium $2 to $8, high over $8.

Coder

Triggered by status:todo on an issue, or agent:coder on a pull request

  • When the issue's turn comes in the queue, it becomes status:in-progress and the coder runs the requirements check, unless the issue has directive:skip-requirements-check.
  • Implements the issue, updates the affected documentation, and opens a pull request from squadron/issue-<number> whose body contains Closes #<number>.
  • Queues the review by applying agent:reviewer to the pull request.
  • On agent:coder, fixes the same pull request using the latest review or tester comment, pushes, and re-applies agent:reviewer. It only follows comments posted with SQUADRON_GITHUB_TOKEN, so other people's comments can't steer it.
  • If a fix makes no changes, it asks the reviewer for a fresh review instead of failing, once per commit. A second run with no changes on the same commit fails and asks a person to step in.
  • After a Squadron tester passed comment, it switches to merge mode and test-merges the base branch first:
    • no conflict: it squash-merges the pull request, or enables auto-merge if a direct merge is blocked;
    • conflicts: it resolves them, pushes a merge commit, comments the conflicting files, and sends the pull request back to the reviewer, so the resolved code is reviewed and tested again.

The agent itself can't push, comment or merge: the workflow does it. It merges only the commit the tester passed, and refuses if the branch changed since. Changes under .github/workflows are discarded, and conflicts there are left to a person.

Reviewer

Triggered by agent:reviewer on a pull request

  • Reviews the code and documentation against the linked issue.
  • Returns a JSON verdict, which the workflow posts as a comment starting with ## Squadron automated review.
  • No blocking findings: the issue becomes status:testing and the pull request gets agent:tester.
  • Blocking findings: the issue goes back to status:in-progress and the pull request gets agent:coder.
  • Never blocks for a missing workflow change or a requirement only a workflow can meet (CI, tagging, releases, deployments): it lists those as a manual follow-up.

Read-only: the run fails if it changes a file, or if its answer has no valid verdict.

Tester

Triggered by agent:tester on a pull request

  • Uses only the issue title and body as its requirements: no docs, pull request description, review comments or agent summaries. It reads code and existing tests only to find setup and entry points.
  • Adds or updates tests matching SQUADRON_TEST_PATHS, and makes sure SQUADRON_TEST_COMMAND works, adding a missing npm script or test dependency if needed. If existing tests already cover the issue, it may change nothing.
  • The workflow commits only test files and npm manifest and lockfile changes, discards everything else, reinstalls dependencies and runs the command itself.
  • Success: a Squadron tester passed on commit <sha> comment and agent:coder on the pull request, so the coder merges that commit. Failure: a comment with the last 80 log lines (starting with Squadron tester failed), the issue back to status:in-progress, and agent:coder on the pull request.

Never weakens tests, uses a no-op command, changes product code, or merges.

Lifecycle

issue  status:todo ── pipeline busy ──▶ queue comment, waits
   │ pipeline free
   ▼
coder  status:in-progress ── requirements missing ──▶ comment + no status
   │ opens PR squadron/issue-N
   ▼ agent:reviewer
reviewer ── changes requested ──▶ status:in-progress + agent:coder ──┐
   │ approved                                                   │
   ▼ status:testing + agent:tester                              │
tester  ── tests failed ──▶ status:in-progress + agent:coder ───────┤
   │ tests pass: agent:coder                                    │
   ▼                                               coder fixes ◀─┘
coder  ── conflicts ──▶ resolve + push + agent:reviewer
   │ no conflict: squash-merge
   ▼
status:done ──▶ next queued issue starts

Jobs are serialized per issue and per pull request, so two runs never work on the same item at once.

One issue at a time

Squadron works on a single issue at a time, so its pull requests never branch from a base that another Squadron pull request is about to change. When an issue gets status:todo:

  • if another open issue is status:in-progress or status:testing, nothing starts, and the new issue gets a comment saying it's queued;
  • otherwise the oldest queued issue starts, which may not be the one you just labeled. A retry (status:todo re-applied to an issue already in progress or testing) goes first.

The pipeline frees up when the pull request merges, when a Squadron pull request is closed without merging, when the issue is closed, when the requirements check sends it back, or when the coder fails before opening a pull request. A next-issue job runs at the end of every Squadron run and whenever an issue closes, so the oldest queued issue starts as soon as the pipeline is free, whatever freed it. Labeling several issues at once is fine: each claim processes the whole queue.

Once its pull request exists, a failed issue keeps the pipeline busy on purpose: it needs a person, and other issues would conflict with its pull request. Retry it with the label named in the failure comment, or free the queue by closing the pull request. If the coder fails before opening a pull request, nothing can conflict yet, so the issue leaves the queue instead: add status:todo to retry it.

Failures and retries

Every failed run comments on its issue or pull request with a link to the run and the label to re-apply.

To retryRe-apply
The coder, before a pull request existsstatus:todo on the issue
A fix on the pull requestagent:coder on the pull request
The reviewagent:reviewer on the pull request
Testingagent:tester on the pull request
The merge, if the branch changed after the tests passedagent:tester on the pull request
A merge-conflict resolutionagent:coder, or resolve them yourself, push, and re-apply agent:reviewer

Conflicts in .github/workflows always need a person. If the coder fix makes no changes twice on the same commit, re-applying agent:coder would repeat the same result: resolve the remaining findings yourself, or update the issue, then re-apply agent:reviewer.

If the coder fails before opening a pull request, the issue loses its status and the next queued issue starts. Once a pull request exists, a failed issue holds the queue until its pull request merges or closes. Closing a Squadron pull request without merging removes its issue's status; add status:todo to queue it again.

Only pull requests from squadron/issue-<number> branches in the same repository are automated. Pull requests you open yourself are left alone.

What agents can't change

Agents never publish changes under .github/workflows. If an issue needs a GitHub Actions workflow (CI, releases, deployments, schedules), the requirements check sends it back until it either limits the scope to what agents can deliver (scripts, configuration, documentation, or an example workflow stored outside .github/workflows) or states that a person will add the workflow.

The reviewer doesn't block a pull request for a missing workflow change: it mentions it as a manual follow-up. Add or change workflow files yourself.

Updating

Run Actions → Squadron Update → Run workflow to copy the latest Squadron files from the template's default branch:

  1. The workflow first compares its own file with the template's. If it changed, it commits the new version as chore: update Squadron update workflow, relaunches itself and stops; the relaunched run does the update.
  2. Otherwise it copies the files listed in the workflow (the Squadron issue forms, scripts, skills and workflows under .github/, plus SQUADRON.md, SQUADRON-CHANGELOG.md and USAGE.md), then commits and pushes them as chore: update Squadron. If nothing changed, it commits nothing.
  3. It then starts the setup workflow, even when nothing changed, so the labels follow the updated template, including removing model labels the template no longer lists.

The listed files are overwritten, so customizations in them will be lost. Your own files under .github/ and README.md are left unchanged, and files removed from the template aren't deleted from your repository.

See the changelog for what each update brings.

Security boundaries

  • Copilot CLI can edit files and run tools, so apply status:todo only to issues that should be processed. Issue text is treated as untrusted input.
  • SQUADRON_GITHUB_TOKEN is never present in a Copilot step, and COPILOT_GITHUB_TOKEN is stripped from Copilot's shell environment.
  • Fork pull requests and pull requests from other branches never get the automation credentials.
  • Helper scripts always run from a checkout of the default branch, never from the pull request under review.
  • Agent changes under .github/workflows are discarded before publishing.
  • The coder only follows Squadron comments posted with SQUADRON_GITHUB_TOKEN, and merges only on a Squadron tester passed comment from that token, and only the commit it names. Other users' comments or later pushes can't trigger a merge of untested code.
  • Agents only switch to models listed in .github/squadron-models.txt; other model labels are ignored.
  • The review is model-generated: treat it as automation feedback, not a substitute for required human review.
  • An issue becomes status:done only after its pull request actually merges.

Architecture

Every job checks out the default branch to squadron/ (trusted scripts and skills) and the product code to product/, where Copilot runs. Copilot CLI is pinned to @github/copilot@1.0.105 in every role workflow.

FileRole
.github/workflows/coder.ymlThe only event listener (workflow Squadron). Routes each issue or pull request event to one job: claim then coder, coder-fix (fixes, or merges after a pass), reviewer, tester, mark-done or release (Squadron pull request closed without merging). The next-issue job runs after every one of them and when an issue closes. Claims share one concurrency group, so two issues can never both take an empty pipeline.
.github/workflows/reviewer.ymlReusable reviewer workflow, called by coder.yml.
.github/workflows/tester.ymlReusable tester workflow, called by coder.yml.
.github/workflows/setup.ymlManual and safe to re-run: creates or updates labels, deletes unlisted model labels, checks the secrets. Also started by the update workflow.
.github/workflows/update.ymlManual: updates itself, syncs the listed template files, then starts the setup.
.github/scripts/set-issue-status-label.shReplaces the issue's status:* label, or removes it.
.github/scripts/claim-next-issue.shThe claim: starts at most one issue and comments on the other queued ones.
.github/scripts/start-next-issue.shWhen the pipeline is free, re-applies status:todo to the oldest queued issue to start it.
.github/scripts/read-issue-directives.shReads the issue's directive:* labels for every job that runs Copilot.
.github/squadron-models.txtThe models agents can switch to, with their cost tier. The single source for the model labels.
.github/scripts/set-agent-label.shClears agent:* labels and optionally adds one, which starts the next agent.
.github/scripts/extract-requirements-report.pyExtracts the requirements verdict and renders the questions comment.
.github/scripts/extract-review-report.pyExtracts the review verdict and renders the review comment.
.github/scripts/install-dependencies.shRuns npm ci or npm install when there's a package.json.
.github/skills/squadron-requirements-checker/What makes an issue ready, and the JSON verdict.
.github/skills/squadron-requirements-helper/Helps people write issues that pass the check.
.github/ISSUE_TEMPLATE/The Feature, Technical task and Bug forms.

Known limits

  • Quality drifts across tickets. Agents don't remember previous issues or share a picture of the system. In my runs, quality had visibly degraded by the fifth ticket.
  • The tester only protects the current issue. Nothing re-checks what earlier issues assumed unless their tests still cover it.
  • One issue at a time. The queue avoids conflicting pull requests, but a failed issue blocks the others until someone handles it.
  • No questions mid-way. Apart from the requirements check up front, agents fill gaps with their own guesses.
  • npm-oriented. Dependency installation and test setup assume an npm project; other stacks need a custom SQUADRON_TEST_COMMAND and may need workflow changes.

More on this in Squadron, or why agents don't fix poor requirements.

FAQ

Do I need a GitHub Project?

No. Status lives in issue labels.

The coder asked questions. Where do I answer?

In the issue body. Agents don't read comments. Then add status:todo again.

Will it touch pull requests I open myself?

No. Only pull requests from squadron/issue-<number> branches in the same repository are automated.

Does the reviewer's approval count as a GitHub review?

No. It's a comment. Branch protection and required checks remain authoritative.

Can I customize the workflows?

Yes, but the update workflow overwrites the Squadron files it lists. Keep customizations in your own files, or don't run updates.

I labeled an issue and nothing happened.

Another issue is probably in progress or testing: yours got a queue comment and will start on its own. If that other issue has failed, retry it or close it to free the queue.

Can I use a different model?

Yes, per issue: add one of the directive:use-model-… labels before the issue starts, and all three agents use that model for it. See issue directives.

My project doesn't use npm.

Set SQUADRON_TEST_COMMAND to your test command and SQUADRON_TEST_PATHS to your test file patterns. Dependency installation only runs when there's a package.json.
