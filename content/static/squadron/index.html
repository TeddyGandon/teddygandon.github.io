A squad of agents

Squadron is an experiment, not a product. A coder, a reviewer and a tester agent try to take a GitHub issue all the way to a merged pull request, handing off with labels and sending the work back when a review or a test fails. It works, up to a point.

01 · Pipeline

A loop, not a line.

Each agent hands off to the next with a label. When a review or a test fails, the same pull request goes back to the coder. When the tests pass, it goes back to the coder too, this time to merge. One issue at a time, so pull requests don't conflict with each other.

Issue status

status:todo status:in-progress status:testing status:done

Handoffs

agent:coder agent:reviewer agent:tester

02 · Agents

Same model. Different eyes.

All three run on the same model. The idea I wanted to test: give each role a different view of the work and clear limits, so they check each other instead of agreeing with themselves.

</>

Coder

Checks the requirements first, then updates the docs, implements the issue and opens the pull request. Fixes it when it comes back, and merges it once the tests pass.

  • Won't start on an issue with blocking gaps
  • Merges only the exact commit the tester passed
◎

Reviewer

Reads the diff against the issue: code, docs, security, architecture. Returns a JSON verdict.

  • Edits a single file? The run fails.
  • No valid verdict? The run fails.
✓

Tester

Writes and runs tests from the issue alone. The workflow runs the tests again itself, then hands the pull request back to the coder to merge.

  • No README, PR description or summaries
  • Never weakens tests or touches product code

Requirements check

Questions before code.

If the issue leaves doubt, the coder comments what's missing and removes its status, so it leaves the queue. Answer in the issue body and add status:todo again. An issue that needs a GitHub Actions workflow is sent back too: agents can't change those files.

Queue

One at a time.

A new status:todo issue waits while another is in progress or testing, then starts on its own, oldest first.

Merge

Conflicts go back through review.

Before merging, the coder checks the pull request against its base branch. If it conflicts, it resolves the conflicts, pushes a merge commit and sends the pull request back to the reviewer and the tester. Conflicts in .github/workflows are left to a person.

Retry

One label away.

Every failure comments a run link and the label to re-apply. A failed issue holds the queue until it's retried or closed.

03 · Setup

Want to try it?

  1. Create your repo from the Squadron template.
  2. Add two secrets: a Copilot token, and a fine-grained token with Contents, Pull requests, Issues and Workflows in read and write.
  3. Run Actions → Squadron Setup once. It creates the labels and checks the secrets.
  4. Open an issue from a form, and add status:todo when it's ready.

Later, Actions → Squadron Update pulls the latest Squadron workflows, scripts, skills and docs from the template, and leaves your own .github/ files alone. Read the full docs →
